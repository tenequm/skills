# SwiftPM and Builds

Package.swift on Swift 6.4, local packages for iOS and macOS apps, resources, plugins, macros, the Swift Build engine, `xcodebuild` basics, Xcode 27 build-breakers, and the macOS-only path of shipping an app straight from SwiftPM.

Verified on Xcode 27.0 (Swift 6.4, iOS 27.0 / macOS 27.0 SDKs), 2026-10-07: built and tested scratch packages covering every manifest snippet (traits, resources, a remote dependency, ObjC target, strict settings, two executables), a build-tool plus command plugin, the `swift package init --type macro` template; assembled, ad-hoc signed and ran a `.app` from `swift build` output; checked flags with `swift build --help`, `swift build --help-hidden`, `swift test --help`, `swift package --help`, `xcodebuild -help`; compiled the conditional-compilation snippet through SIL (`swiftc -emit-sil`) for iOS and macOS; read `PackageDescription` and `PackagePlugin` interfaces; reproduced four of the five Xcode 27 build-breakers and checked all five against the [Xcode 27 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes); the agent-sandbox errors are quoted from two earlier Codex sandbox sessions, not reproduced.

## Package.swift on Swift 6.4

SwiftPM alone cannot produce an iOS `.app` (no Info.plist, entitlements, asset catalogs or signing for iOS). An iOS app is an Xcode project (generated by XcodeGen, see ios-project-setup.md) that depends on local packages. A macOS app can be either; see the macOS section at the end.

The default shape: logic in a local package that builds for both platforms, so `swift test` runs it on the Mac (see testing.md):

```swift
// swift-tools-version: 6.4
import PackageDescription

let package = Package(
    name: "AppCore",
    platforms: [.iOS(.v26), .macOS(.v15)],
    products: [.library(name: "AppCore", targets: ["AppCore"])],
    targets: [
        .target(name: "AppCore"),
        .testTarget(name: "AppCoreTests", dependencies: ["AppCore"]),
    ]
)
```

- `swift package init` on this toolchain writes `// swift-tools-version: 6.4`. The tools version gates manifest API: `.iOS(.v26)` / `.macOS(.v26)` need 6.2, `.iOS(.v27)` / `.macOS(.v27)` need 6.4. Xcode 26 cannot open a 6.4 manifest - stay on 6.2 if collaborators are still on Xcode 26.
- Tools version 6.0+ defaults every target to the Swift 6 language mode; `.swiftLanguageMode(.v6)` is only needed to be explicit or to override a `.v5` default elsewhere.
- `platforms` sets minimums, not the platform list: a package builds for every platform, and the minimum for an unlisted one is the oldest SwiftPM supports.
- New templates (`swift package init --type library|executable|tool|macro|build-tool-plugin|command-plugin|empty`) add `.enableUpcomingFeature("ApproachableConcurrency")` to each target. In Swift 6.4 that name turns on the approachable-concurrency feature set (verified: it enables isolated conformance inference, like `InferIsolatedConformances`); see concurrency-isolation.md.

## Swift settings

```swift
.target(
    name: "AppCore",
    swiftSettings: [
        .swiftLanguageMode(.v6),
        .defaultIsolation(MainActor.self),                   // unannotated code is @MainActor
        .enableUpcomingFeature("ExistentialAny"),
        .strictMemorySafety(),                               // SE-0458; replaces the experimental flag
        .treatAllWarnings(as: .error),
        .treatWarning("DeprecatedDeclaration", as: .warning), // carve-out from the line above
    ]
)
```

Traps:
- **Misspelled feature names are silently ignored.** `-enable-upcoming-feature BogusFeatureX` compiles with no warning. Check names against `swiftc -print-supported-features` (JSON listing every upcoming, experimental and optional feature this compiler knows).
- **`.defaultIsolation(MainActor.self)` changes the package's public API.** Every unannotated public function and type becomes `@MainActor`, so callers in other modules - including the package's own test target, which is nonisolated - fail with `call to main actor-isolated global function '...' in a synchronous nonisolated context`. Use it on UI-facing targets; leave model/network/parsing targets nonisolated, or mark the tests `@MainActor`.
- `.unsafeFlags` makes a package unusable as a version-based dependency; keep it to local packages and the root.

## Dependencies and traits

```swift
dependencies: [
    .package(url: "https://github.com/org/repo", from: "1.0.0"),            // >= 1.0.0, < 2.0.0
    .package(url: "https://github.com/org/repo", exact: "1.2.3"),
    .package(url: "https://github.com/org/repo", "1.0.0"..<"1.5.0"),
    .package(url: "https://github.com/org/repo", revision: "abc123"),
    .package(url: "https://github.com/org/repo", branch: "main"),          // not allowed in a package others depend on by version
    .package(path: "../LocalPackage"),
],
targets: [
    .target(
        name: "AppCore",
        dependencies: [
            .product(name: "Collections", package: "swift-collections",
                     condition: .when(platforms: [.macOS, .iOS])),
        ]
    ),
]
```

Package traits (SE-0450) are additive feature flags a consumer opts into:

```swift
let package = Package(
    name: "AppKitchen",
    traits: [
        .default(enabledTraits: ["Networking"]),
        "Networking",
        .trait(name: "Experimental", enabledTraits: ["Networking"]),
    ],
    targets: [
        .target(name: "AppCore", swiftSettings: [
            .define("NETWORKING", .when(traits: ["Networking"])),
        ]),
    ]
)

// Consumer
.package(url: "https://github.com/org/appkitchen", from: "1.0.0", traits: ["Experimental"]),
```

`swift package show-traits` lists them; `swift build --traits A,B`, `--enable-all-traits` and `--disable-default-traits` exercise combinations locally (passing `--traits` replaces the defaults unless you include `defaults`). Traits must be strictly additive: enabling one must never remove API, because two consumers in one graph can enable different sets and get one unified build.

## Resources

```swift
.target(name: "AppCore", resources: [
    .process("Resources"),          // platform-optimized (asset catalogs, xibs, strings compiled)
    .copy("Data/config.json"),      // byte-for-byte
])
```

```swift
guard let url = Bundle.module.url(forResource: "config", withExtension: "json") else {
    throw CocoaError(.fileNoSuchFile)
}
```

Each target with resources gets a `<Package>_<Target>.bundle` next to the products and a generated `Bundle.module`. If that bundle is missing at runtime, `Bundle.module` does not return nil - **it calls `fatalError("unable to find bundle named <Package>_<Target>")`**. It searches `Bundle.main.resourceURL`, the enclosing framework's resources, then `Bundle.main.bundleURL`. Xcode copies the bundle for you; hand-assembled apps must copy it (macOS section).

## Other target kinds, mixed ObjC

```swift
.binaryTarget(name: "Vendor", path: "Vendor.xcframework"),
.binaryTarget(name: "Remote", url: "https://example.com/Remote.xcframework.zip", checksum: "<swift package compute-checksum>"),
.systemLibrary(name: "CZlib", pkgConfig: "zlib"),
```

A target is all Swift or all C-family. Put ObjC in its own target with a public header directory; the common case is catching `NSException`s that Swift cannot catch (AVFoundation's `installTap`, KVC, collection bounds in ObjC APIs):

```
Sources/
  AppFeature/Feature.swift
  ObjCExceptionCatcher/
    include/ObjCExceptionCatcher.h
    ObjCExceptionCatcher.m
```

```swift
.target(name: "ObjCExceptionCatcher", publicHeadersPath: "include"),
.target(name: "AppFeature", dependencies: ["ObjCExceptionCatcher"]),
```

```objc
// include/ObjCExceptionCatcher.h
#import <Foundation/Foundation.h>

NS_ASSUME_NONNULL_BEGIN
@interface ExceptionCatcher : NSObject
+ (BOOL)catchException:(NS_NOESCAPE void (^)(void))block error:(NSError **)error;
@end
NS_ASSUME_NONNULL_END
```

```objc
// ObjCExceptionCatcher.m
#import "ObjCExceptionCatcher.h"

@implementation ExceptionCatcher
+ (BOOL)catchException:(NS_NOESCAPE void (^)(void))block error:(NSError **)error {
    @try {
        block();
        return YES;
    } @catch (NSException *exception) {
        if (error) {
            *error = [NSError errorWithDomain:exception.name code:0
                                     userInfo:@{NSLocalizedDescriptionKey: exception.reason ?: @""}];
        }
        return NO;
    }
}
@end
```

```swift
import ObjCExceptionCatcher

try ExceptionCatcher.catchException { _ = NSArray().object(at: 3) }  // throws instead of crashing
```

It must be an ObjC *method* with a trailing `NSError **`: only those import as Swift `throws`. A plain C function with the same signature imports as a two-argument function (`missing argument for parameter #2 in call`).

## Plugins

`PackagePlugin` uses `URL` throughout; the `Path` APIs (`directory`, `pluginWorkDirectory`, `.path` on tools) are deprecated since tools 6.0. A build-tool plugin that generates Swift from `*.keys` files in the target, using an executable target of the same package as the tool:

```swift
// Package.swift
targets: [
    .executableTarget(name: "GenTool"),
    .plugin(name: "GenPlugin", capability: .buildTool(), dependencies: ["GenTool"]),
    .target(name: "Lib", plugins: ["GenPlugin"]),
]
```

```swift
// Plugins/GenPlugin/plugin.swift
import Foundation
import PackagePlugin

@main
struct GenPlugin: BuildToolPlugin {
    func createBuildCommands(context: PluginContext, target: Target) throws -> [Command] {
        guard let module = target as? SourceModuleTarget else { return [] }
        return try module.sourceFiles(withSuffix: "keys").map { file in
            let output = context.pluginWorkDirectoryURL
                .appending(path: file.url.deletingPathExtension().lastPathComponent + ".swift")
            return .buildCommand(
                displayName: "Generate \(output.lastPathComponent)",
                executable: try context.tool(named: "GenTool").url,
                arguments: [file.url.path(), output.path()],
                inputFiles: [file.url],
                outputFiles: [output]
            )
        }
    }
}
```

Declare every input and output: they drive incremental rebuilds, and outputs ending in `.swift` are compiled into the target.

Command plugins run on demand (`swift package <verb>`) and are sandboxed; writing to the package or using the network must be declared and then allowed on the command line:

```swift
.plugin(name: "StampPlugin", capability: .command(
    intent: .custom(verb: "stamp", description: "Write a BUILD_STAMP file"),
    permissions: [
        .writeToPackageDirectory(reason: "Writes BUILD_STAMP"),
        // .allowNetworkConnections(scope: .all(ports: [443]), reason: "Fetches schema"),
    ]
)),
```

```swift
// Plugins/StampPlugin/plugin.swift
import Foundation
import PackagePlugin

@main
struct StampPlugin: CommandPlugin {
    func performCommand(context: PluginContext, arguments: [String]) throws {
        let stamp = context.package.directoryURL.appending(path: "BUILD_STAMP")
        try Date.now.ISO8601Format().write(to: stamp, atomically: true, encoding: .utf8)
    }
}
```

```bash
swift package plugin --list
swift package --allow-writing-to-package-directory stamp
```

Without the flag, a non-interactive run prints `error: Plugin 'StampPlugin' wants permission to write to the package directory.` and **still exits 0** - check for the output file, not the exit code. For Xcode builds of plugin-using dependencies, see xcodebuild basics.

## Macros

Start from the template; it pins swift-syntax to the toolchain's release line (604.x for Swift 6.4):

```bash
swift package init --type macro --name Stringify
```

```swift
import CompilerPluginSupport  // required for .macro targets

dependencies: [
    .package(url: "https://github.com/swiftlang/swift-syntax.git", from: "604.0.0-latest"),
],
targets: [
    .macro(name: "StringifyMacros", dependencies: [
        .product(name: "SwiftSyntaxMacros", package: "swift-syntax"),
        .product(name: "SwiftCompilerPlugin", package: "swift-syntax"),
    ]),
    .target(name: "Stringify", dependencies: ["StringifyMacros"]),
    .testTarget(name: "StringifyTests", dependencies: [
        "StringifyMacros",
        .product(name: "SwiftSyntaxMacrosTestSupport", package: "swift-syntax"),
    ]),
]
```

SwiftPM downloads prebuilt swift-syntax (`--enable-experimental-prebuilts` is on by default; cached under `.build/prebuilts`), so a cold `swift test` of the template takes about 40 s instead of compiling swift-syntax from source.

## Swift Build is the default engine

In SwiftPM 6.4, `--build-system` defaults to `swiftbuild` (Xcode's open-source build engine); `native` and `xcode` are deprecated. Consequences:

- **Products live in `.build/out/Products/Debug|Release`**, not `.build/arm64-apple-macosx/release`. `.build/debug` and `.build/release` are symlinks to them. Scripts should always ask: `BIN=$(swift build -c release --show-bin-path)`.
- Modules are built explicitly, with caches inside the scratch path.
- Universal binaries come from SwiftPM directly. `--arch` is a hidden flag (only in `swift build --help-hidden`):

```bash
swift build -c release --arch arm64 --arch x86_64
lipo -info "$(swift build -c release --arch arm64 --arch x86_64 --show-bin-path)/MyTool"
```

This prints `warning: The x86_64 architecture is deprecated for your deployment target (macOS 27.0)` even when the package's real minimum is lower (seen with `.macOS(.v15)`; both slices have `minos 15.0`). The universal binary is still produced; the warning is noise below a macOS 27 deployment target.

Other useful flags: `--explicit-target-dependency-import-check error` (fails a target that imports a module it does not declare), `--sbom-spec cyclonedx|spdx` (SBOM generation), `swift package add-dependency|add-target|add-product|add-setting` (edit the manifest from the CLI).

## Conditional compilation

```swift
#if os(macOS)
import AppKit
typealias PlatformImage = NSImage
#elseif os(iOS)
import UIKit
typealias PlatformImage = UIImage
#endif

#if canImport(FoundationModels)
import FoundationModels
#endif

#if compiler(>=6.4)
let modernCompiler = true
#else
let modernCompiler = false
#endif

#if targetEnvironment(simulator)
let isSimulator = true
#else
let isSimulator = false
#endif
```

`canImport` answers "is the module in this SDK", not "is it available at runtime" - pair it with `if #available` for OS-gated APIs. `#if DEBUG` is set by SwiftPM debug builds and by Xcode's Debug configuration.

## CI and headless traps

**Unwritable `$HOME` caches.** In sandboxes, CI containers and agent shells, `swift build` can fail during manifest compilation - before your sources - because SwiftPM's shared cache lives under the home directory. The error names SwiftPM internals and reads like a broken package. Redirect and retry before debugging the package:

```bash
swift build --cache-path "$SCRATCH/spm-cache" --scratch-path "$SCRATCH/build"
```

Under Swift Build the module cache lives in the scratch path, so the old `-Xswiftc -module-cache-path` redirect is no longer needed.

Agent sandboxes can block more than the cache. Inside the Codex `workspace-write` sandbox an unsigned `xcodebuild ... -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO build` failed with (abbreviated):

```
Could not resolve package dependencies: error opening '~/.cache/clang/ModuleCache/...': Operation not permitted
Unable to discover any Simulator runtimes ... simdiskimaged ... launchd job is not registered
```

The first is the same `$HOME` cache problem; the second is `xcodebuild` failing to reach CoreSimulator's launchd services, which no path redirect fixes. Run the build with sandbox escalation (outside the sandbox) instead of debugging the project (seen in two Codex sessions; not reproduced in other sandboxes).

**Plugin and macro trust prompts.** A project whose dependencies carry package plugins or macros stops headless `xcodebuild` on `Validate plug-in '<name>' in package '<pkg>'`. Skip validation only for vetted dependencies - it is the trust boundary for code that runs at build time:

```bash
xcodebuild -scheme MyApp -skipPackagePluginValidation -skipMacroValidation
```

**Metal toolchain is a separate component.** Any target compiling `.metal` shaders, directly or through a dependency, fails until the Metal toolchain component is installed:

```bash
xcodebuild -showComponent MetalToolchain   # Status: installed / not installed
xcodebuild -downloadComponent MetalToolchain
```

## xcodebuild basics

```bash
xcodebuild -list                                                     # schemes and targets (also works in a package dir)
xcodebuild -showdestinations -scheme MyApp
xcodebuild build -scheme MyApp -destination 'generic/platform=iOS' CODE_SIGNING_ALLOWED=NO
xcodebuild build -scheme MyApp -destination 'generic/platform=iOS Simulator'
xcodebuild test  -scheme MyApp -destination 'platform=iOS Simulator,name=Test iPhone' \
  -only-testing:MyAppTests -resultBundlePath build/tests.xcresult
xcodebuild build -scheme MyMacApp -destination 'platform=macOS'
```

- `generic/platform=iOS` compile-checks for devices with no device attached and no simulator runtime needed; `CODE_SIGNING_ALLOWED=NO` skips signing for a pure compile check. A generic iOS build of a small SwiftUI app took 7 s.
- `-derivedDataPath build` keeps products in the repo-local `build/` for scripts and CI caches.
- Repeating and flake hunting: `-test-iterations N`, `-retry-tests-on-failure`, `-run-tests-until-failure`. Enumerate without running: `-enumerate-tests`.
- Interface Builder documents for UIKit now compile in a `toolchain` mode by default, without a simulator runtime; `IBC_COCOATOUCH_COMPILER_MODE = simulator` restores the old behavior.
- Signing, archiving and export are in ios-distribution.md and macos-distribution.md.

## Xcode 27 build-breakers

These hit the first time a project builds with Xcode 27, before any new API is adopted. All five are in the [Xcode 27.0 release notes](https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes); Xcode 27 requires macOS Tahoe 26.6 or later and runs only on Apple silicon.

**ld64 is removed.** "The ld64 linker has been removed and the `-ld_classic` option is no longer supported." In practice the flag is ignored with `ld: warning: -ld_classic is no longer supported and will be ignored` - the link succeeds, so it only fails builds that treat linker warnings as errors, or that relied on an ld64-only behavior the flag was added to work around. Delete `-ld_classic` from `OTHER_LDFLAGS` / `linkerSettings` and retest whatever it was papering over.

**Clang module names must be unique per dependency scan.** The faster Swift dependency scanner requires every Clang module reachable from one scan to have a unique name. Two `module.modulemap` files declaring the same module both on the header search path now fail with:

```
error: redefinition of module 'Dup'
note: previously defined here
```

The usual cause is vendored third-party sources shipping a `module.modulemap` that redeclares an SDK module or another vendored copy. Delete the duplicate or rename one module.

**No x86_64 by default at macOS 27.** `ARCHS_STANDARD` drops x86_64 when `MACOSX_DEPLOYMENT_TARGET` (or `DRIVERKIT_DEPLOYMENT_TARGET`) is 27.0 or later. Verified: a macOS target at 26.0 resolves `ARCHS_STANDARD = arm64 x86_64`, at 27.0 `arm64`. If you still ship Intel, set `ARCHS = arm64 x86_64` explicitly or keep the deployment target below 27. The macOS 27 SDK still back-deploys universal apps to macOS 12.

**SE-0508 source break: `init` accessor order.** A computed property with an `init` accessor and an array or dictionary literal initial value no longer compiles if the getter comes first - and the diagnostic does not mention the cause:

```swift
struct Box {
    private var storage: [Int]
    var items: [Int] = [] {
        get { storage }
        @storageRestrictions(initializes: storage) init { storage = newValue }
        // error: initializers may only be declared within a type
        set { storage = newValue }
    }
}
```

Fix: declare the `init` accessor first, then `get`, then `set`.

**libc++ floor and behavior changes.** The minimum macOS deployment target for the C++ standard library is now 11.0. `std::multimap` / `multiset::find` no longer necessarily returns the first equal element - use `lower_bound` or `equal_range` when you need it. `std::map` / `set` `lower_bound` / `upper_bound` change results for comparators that are not a strict weak order (temporary escape hatch: define `_LIBCPP_ENABLE_LEGACY_TREE_LOWER_UPPER_BOUND`), and `bitset::operator[] const` now returns `bool`.

## macOS only: an app straight from SwiftPM

For a menu-bar utility or agent-style app, a pure SwiftPM project plus a small bundle step is a valid alternative to an Xcode project. `swift build` produces a bare executable; macOS needs a `.app` for Info.plist keys (`LSUIElement`, usage descriptions), TCC attribution, entitlements and embedded frameworks.

```bash
set -euo pipefail
BIN=$(swift build -c release --show-bin-path)
APP=build/MyApp.app
rm -rf "$APP"
mkdir -p "$APP/Contents/MacOS" "$APP/Contents/Resources" "$APP/Contents/Frameworks"
cp "$BIN/MyApp" "$APP/Contents/MacOS/"
cp Info.plist "$APP/Contents/"                       # CFBundleExecutable must equal the binary name
cp -R "$BIN"/*.bundle "$APP/Contents/Resources/"     # SwiftPM resource bundles
# Copy any dynamic frameworks the app links (e.g. a binaryTarget .xcframework slice) into Contents/Frameworks.
install_name_tool -add_rpath @executable_path/../Frameworks "$APP/Contents/MacOS/MyApp"
# Sign inside-out: nested frameworks/helpers first, the app last.
codesign --force --options runtime --timestamp --sign "$SIGN_ID" \
  --identifier com.example.MyApp --entitlements entitlements.plist "$APP"
```

Verified end to end with an executable that reads a resource through `Bundle.module` (ad-hoc signed with `--sign -`, `codesign --verify --strict` clean, resource found at runtime). Gotchas:
- **rpath:** SwiftPM's executable never gets `@executable_path/../Frameworks` (it may get `@loader_path`, plus toolchain paths from the build machine). Without `-add_rpath`, a bundled dynamic framework crashes at launch with `dyld: Library not loaded: @rpath/...`.
- **Resource bundles are not copied for you**, and a missing one is a `fatalError` in `Bundle.module`, on the first access, often only on machines other than the build machine (where `Bundle.main.bundleURL` happened to point at `.build`).
- **Nested code** (frameworks, XPC services, helper executables in `Contents/MacOS`) is signed before the app that contains it. Notarization, hardened runtime and entitlements are in macos-distribution.md.
- **Stale read-only artifacts** from earlier copies make `cp` fail; `rm -rf` the bundle before assembling.

Helper executables are additional `executableTarget`s copied into `Contents/MacOS/` and signed before the app:

```swift
targets: [
    .executableTarget(name: "MyApp", swiftSettings: [.defaultIsolation(MainActor.self)]),
    .executableTarget(name: "MyWatchdog", path: "Sources/Watchdog",
                      swiftSettings: [.treatAllWarnings(as: .error)]),
]
```

Unverified: relaunching by rebuilding in place while the old process still runs gets the new process killed with `SIGKILL (Code Signature Invalid)`; a run recipe should `killall MyApp` and wait for it to exit (`while killall -0 MyApp 2>/dev/null; do sleep 0.1; done`) before copying the new binary, and `open` does not relaunch an already-running `LSUIElement` app.

**Command Line Tools only (no Xcode).** With `DEVELOPER_DIR=/Library/Developer/CommandLineTools` (CLT 27.0, Swift 6.4), Swift Testing works out of the box - `swift test` built and ran a 10-test package with no extra flags, so the old `-F .../CommandLineTools/Library/Developer/Frameworks` `unsafeFlags` workaround is obsolete. XCTest is absent: any `import XCTest` fails the build with `unable to resolve module dependency: 'XCTest'`. Keep CLT-only machines on Swift Testing, and check `xcode-select -p` when a test target behaves differently on CI than locally.
